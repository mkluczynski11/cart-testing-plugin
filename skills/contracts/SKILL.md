# contracts

Formats only; no procedure. Paths are relative to the tester's `e2e/` directory. When a format here and the output of
`qa-harness` disagree, the harness is right: report the difference.

More, read when needed: driver types and the UI boundary in `${CLAUDE_SKILL_DIR}/driver.md`; the intent review, the run
review, the defects file and the run evidence in `${CLAUDE_SKILL_DIR}/reviews.md`.

## Scenario: `specs/<slug>.md`

A YAML front matter between `---` lines, then a short description for people (it does not affect the test). The
grammar is closed: no other fields.

```yaml
---
id: <slug>                     # equal to the file name; lowercase letters, digits, hyphens
title: <what the test shows, one line>
app: <app>                     # equal to "app" in qa.config.json
status: draft                  # draft | confirmed; only `qa-harness example <slug> --confirm` sets confirmed
request: "<the tester's words, verbatim>"
products:
  A: { pick: first-available }
  B: { pick: next-available, distinct_from: [A] }
steps:
  - { id: S1, do: add,    product: A, qty: 1, cart_after: { A: 1 } }
  - { id: S2, do: add,    product: B, qty: 1, cart_after: { A: 1, B: 1 } }
  - { id: S3, do: setQty, product: A, qty: 3, cart_after: { A: 3, B: 1 } }
  - { id: S4, do: remove, product: B,         cart_after: { A: 3 } }
check: each-step               # each-step | last-step | [S2, S4]
preconditions: [empty-cart, guest, no-geolocation]
price_source: ui               # ui | api
---
```

- **Aliases** are upper-case letters and digits (`A`, `B`, `P2`). Every declared alias is used by a step.
- **Picks.** `{ pick: first-available }`; `{ pick: next-available, distinct_from: [<every earlier unnamed alias>] }`;
  `{ pick: by-name, name: "<exact product name>" }` only when the tester named the product. A required attribute is
  `where: { <attr>: [<value>, ...] }` on an unnamed pick. An unnamed pick never selects a product named in the scenario.
- **Steps.** `id` `S1`, `S2`, … unique; `do` is `add`, `setQty` or `remove`; `qty` is a whole number for `add` and
  `setQty` and absent for `remove`; `cart_after` is the whole cart after the step (`{}` for an empty cart).
- **`check`** names the checkpoints; the last step always has one.
- **`price_source`** comes from `qa.config.json` (`priceSource`) unless the tester says otherwise.

### Step semantics (the same table in the ledger, the reference cart and the validator)

| Step | Condition | Effect |
| --- | --- | --- |
| `add P n` | `n` ≥ 1 | no line for P: a new line with quantity `n`; a line exists: its quantity grows by `n` |
| `setQty P n` | P is in the cart; `n` ≥ 1 and differs from the current quantity | the quantity of P equals `n` |
| `remove P` | P is in the cart | the line disappears; the cart may become empty |

A unit price is read at the first add and stays constant. There is no `setQty` to zero: that is `remove`.

### Validation (`qa-harness example` and `compile` answer `SPEC_INVALID` with the rule numbers)

| Rule | Requirement |
| --- | --- |
| V1 Schema | required fields, known values, unique step ids, `id` equal to the file name, no unknown field |
| V2 References | every step names a declared alias; every alias is used |
| V3 Different products | unnamed picks list every earlier unnamed alias in `distinct_from`; `by-name` does not repeat a name |
| V4 Step conditions | each step meets the condition of the semantics table |
| V5 A step changes state | `setQty` to the current quantity is an error |
| V6 State agreement | each `cart_after` equals the state the ledger computes |
| V7 Checkpoints | `check` names existing steps; the last step has a checkpoint |
| V8 Purchase constraints | no state in `cart_after` exceeds a limit of the rules file |

### Freeze

`qa-harness example <slug>` computes the example on stub prices and writes `specs/<slug>.example.json`; on a confirmed
scenario it only prints the example and the freeze state, and the file with its confirmation record stays as it is.
`qa-harness example <slug> --confirm` sets `status: confirmed` and records `confirmed.scenarioSha256` (the contract
fields without `status`) and `confirmed.rulesSha256`. Any later change to the contract fields or to
`app/<app>.pricing.ts` makes `compile` and `run` refuse (`SPEC_INVALID`, `SCENARIO_CHANGED`) until a new confirmation.

## Example: `specs/<slug>.example.json`

Written by the harness only: `stub` (placeholder prices and attributes per alias), `rules`, `expected` (per checkpoint:
cart, subtotal, adjustments, total), `gaps`, and after the confirmation `confirmed`. Stub prices claim nothing about
the application; real prices appear only in a live run.

## Test: `tests/<slug>.spec.ts`

Written only by `qa-harness compile <slug>`; one `shopper` call per step, in order, and `checkTotal` per checkpoint.

```ts
// GENERATED by qa-harness compile. Change the scenario, not this file.
// scenario: <slug> · sha256:<scenario hash>
// request: <the tester's words>
// body-sha256: <hash of the body>
import { test } from '../support/core/fixtures';

test.use({ preconditions: ['empty-cart', 'guest', 'no-geolocation'], priceSource: 'ui' });

test('<title>', async ({ shopper }) => {
  const a = await shopper.add({ pick: 'first-available', filters: { needQty: 3 } }, 1);
  await shopper.checkTotal('S1');
  await shopper.setQuantity(a, 3);
  await shopper.checkTotal('S2');
  await shopper.remove(a);
  await shopper.checkTotal('S3');
});
```

- Allowed calls: `shopper.add(pick | ref, qty)`, `shopper.setQuantity(ref, qty)`, `shopper.remove(ref)`,
  `shopper.checkTotal('<step id>')`.
- Forbidden in a test (gate G0): fixed waits (`waitForTimeout`), `test.skip`/`fixme`/`only`, `expect`, amount
  literals, `try`/`catch` or `if` around actions and checkpoints, environment variables, `page`, imports from outside
  `support/core`.
- The header hash tells an untouched compilation from a hand edit: `compile` overwrites the first and answers
  `FILE_CONFLICT` for the second unless `--force`.

## Rules file: `app/<app>.pricing.ts`

Data, not code: `summary` (labels of the total and subtotal rows), `rules` (pricing rules: condition `always`,
`shareOfUnits`, `hasUnits` or `subtotalAtLeast`; amount as a percentage of the subtotal or of the running value, or
fixed), `constraints` (purchase limits). Every entry carries `provenance: { source: code | tester | observed, ref, live }`.
Only the tester's answer changes it, and every change invalidates the confirmed examples.

## Configuration: `qa.config.json`

`app`, `baseURL`, `testIdAttribute`, `locale`, `currency`, `browserDriver`, `priceSource`, `defects`
(`default` | `extended`), `repeat`, `pickLimit`, `timeouts` (`probeMs`, `actionMs`, `settleMs`, `testMs`), and the
optional `browserAllowedOrigins` (exact origins the page-reading browser may open besides `baseURL`, e.g. the
application's API). Written by `qa-harness init`; a starter pack supplies its defaults.

## Harness commands the flow relies on

- `qa-harness intent <slug>`: `PASS` only for a current `INTENT_OK` review; prints `scenario_sha256: <hash>` to copy and
  ends with a `state:` line (`missing`, `stale`, `unreadable`, `not-confirmed`, `current <VERDICT>`). `verify` records
  that hash in `verification.json` (`intentSha256`), and `doctor` reports a stale review of a verified scenario as
  `VERIFICATION_STALE`.
- `qa-harness report <slug> --promote <runId>`: promotes only a live run whose `verification.json` is `PASS` through
  G4; anything else is refused with the run's own verdict (`NO_TESTS_RUN` for a dry run or one without G4) and the
  tracked files stay as they were. `--as-evidence` (the tester's choice only) keeps an `ORACLE_MISMATCH` or
  `UNMODELED_ADJUSTMENT` live run as evidence and still ends with that verdict.
- A failed driver call in `run`/`verify` names the step and the method: `LOCATOR_FAIL` for a locator timeout or a call
  over 3 × `actionMs`, `UNDETERMINED` for any other exception, `INFRA_FAIL` for the environment.
